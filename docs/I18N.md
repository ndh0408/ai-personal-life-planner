# Internationalization (i18n)

LifeOS AI ships with first-class support for **Vietnamese (`vi`)** and **English (`en`)** from day one. This doc describes how the pieces fit together: mobile UI strings, backend error codes, AI response language, and user-chosen locale storage.

## Supported locales

| Code | Name | Default |
| --- | --- | --- |
| `vi` | Tiếng Việt | **Yes** — when no signal is available |
| `en` | English | Fallback for missing translation keys |

New locales require: a new file under `apps/mobile/src/i18n/locales/`, adding the tag to `SUPPORTED_LOCALES`, updating backend `locale.constants.ts`, adding a migration default if applicable, and translating every key.

## Mobile architecture

### Layout

```
apps/mobile/src/i18n/
  index.ts              # i18next bootstrap + setLocale() + detectDeviceLocale()
  useErrorMessage.ts    # Hook that maps backend errorCode → localized string
  locales/
    vi.json
    en.json
```

### Startup flow

1. `App.tsx` calls `initI18n()` **before** rendering any screen (guarded with a splash).
2. `initI18n()` resolves the initial locale in this order:
   1. **AsyncStorage** under key `lifeos.locale` — wins if valid. User-chosen, sticky.
   2. **Device locale** via `expo-localization` — if the base tag (`vi` or `en`) is one of the supported tags.
   3. **`vi`** — default per product spec.
3. i18next is initialized with the chosen locale and fallback `en`.

### Using translations

```tsx
import { useTranslation } from 'react-i18next';

function HomeHeader() {
  const { t } = useTranslation();
  return <Text>{t('today.greeting', { name: user.displayName })}</Text>;
}
```

**Rules:**
- Never inline a user-facing string in a component. Put it in `vi.json` + `en.json` and use `t('key')`.
- Interpolations use `{{ name }}` syntax.
- Plurals (when needed) use i18next's `_one` / `_other` suffixes.
- New keys are added to **both** locale files in the same PR. CI should fail on key drift.

### Changing the language

```ts
import { setLocale } from './src/i18n';
await setLocale('en'); // persists + hot-swaps
```

All components using `useTranslation` re-render automatically.

### Error translation

The backend returns a stable `errorCode`. The mobile app translates it:

```tsx
import { useErrorMessage } from './src/i18n/useErrorMessage';

const translateError = useErrorMessage();
try { await api.post('/auth/login', body); }
catch (err) { setError(translateError(err)); }
```

Unknown codes fall back to `errors.UNKNOWN_ERROR`. Raw backend strings never reach the user.

## Backend architecture

### Locale resolution

`common/i18n/locale.service.ts::forUser(userId, req)` resolves the active locale for authenticated requests in this order:

1. **`UserProfile.locale`** — what the user selected in settings, persisted via `PUT /api/profile`.
2. **`Accept-Language`** header — parsed by `LocaleMiddleware` into `req.locale`.
3. **`vi`** — fallback.

For anonymous endpoints, only steps 2 and 3 apply.

### UserProfile schema

```prisma
model UserProfile {
  // ...
  locale  String  @default("vi")
}
```

Migration: `prisma/migrations/20260424071200_add_profile_locale/migration.sql`.

### Accept-Language header from mobile

The mobile API client automatically attaches the active locale:

```ts
// apps/mobile/src/services/api/client.ts
headers: {
  ...,
  'Accept-Language': getActiveLocale(),
}
```

So every API call carries the user's locale, even before login.

### Error codes

`AllExceptionsFilter` returns a stable machine-readable `errorCode`:

```json
{ "success": false, "errorCode": "AUTH_INVALID_CREDENTIALS", "message": "…", "statusCode": 401 }
```

See [AUTH_FLOW.md](./AUTH_FLOW.md) for the complete code list. The `message` field is for developers / logs; UX must branch on `errorCode`.

Custom errors can opt into a specific code:

```ts
throw new BadRequestException({
  message: 'Query param "date" must be YYYY-MM-DD',
  errorCode: 'VALIDATION_FAILED',
});
```

### AI responses in the user's locale

When the AI service builds a prompt, it reads `locale = await localeService.forUser(userId, req)` and includes a system instruction: *"Reply in {{language}}"*. This is handled centrally in `AiModule`, so no call site needs to thread the locale through.

### Notifications in the user's locale

Scheduled notifications (reminders for wake-up, meals, habits) read the user's locale at send time, not at schedule time, so a user who switches languages will immediately see the new language in the next reminder.

## Workflow for adding a new key

1. Decide the key path. Group by screen/feature: `today.greeting`, `tasks.priority.HIGH`, `errors.AUTH_EMAIL_TAKEN`.
2. Add the Vietnamese value to `apps/mobile/src/i18n/locales/vi.json`.
3. Add the English value to `apps/mobile/src/i18n/locales/en.json` with matching structure.
4. Use `t('your.key')` in the component.
5. If the key is a backend-originated error, also add it to the `errors.*` block in both locales.

## Do / don't

| ✅ Do | ❌ Don't |
| --- | --- |
| `t('common.save')` | `'Save'` in a Button prop |
| Branch on `err.body.errorCode` | Branch on `err.message.includes('email')` |
| Ship both locales in one PR | Merge an `en.json`-only change |
| Read `getActiveLocale()` on API call | Cache a locale at app start |
